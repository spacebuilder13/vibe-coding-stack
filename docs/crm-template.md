# The Intelligent CRM — Bible

> One brain, many faces. Raw input from anywhere → structured intelligence → any CRM platform.

This document defines how scattered, messy input (call transcripts, WhatsApp exports, video notes, form submissions, voice memos) becomes structured, queryable CRM data. It is the contract between the world and our intelligence layer.

**Core principle:** the logic is portable. Attio is just today's destination. Tomorrow it could be HubSpot, Notion, a custom database, or three of them at once. The schema, the extraction rules, and the prompts live in *this* repo — the sink is a thin adapter.

---

## 1. The Pipeline

```
┌──────────────────┐    ┌──────────────────┐    ┌──────────────────┐    ┌──────────────────┐
│   RAW INPUT      │ →  │   NORMALISER     │ →  │   EXTRACTOR      │ →  │   SINK ADAPTER   │
│                  │    │                  │    │                  │    │                  │
│ • Transcripts    │    │ • Strip noise    │    │ • LLM + schema   │    │ • Attio          │
│ • WhatsApp       │    │ • Plain text     │    │ • Returns JSON   │    │ • HubSpot        │
│ • Video / audio  │    │ • Chunk if long  │    │ • Validated      │    │ • Notion         │
│ • Forms          │    │ • Merge sessions │    │                  │    │ • CSV / Sheets   │
└──────────────────┘    └──────────────────┘    └──────────────────┘    └──────────────────┘
                                                          │
                                                          ▼
                                                ┌──────────────────┐
                                                │  CANONICAL JSON  │
                                                │                  │
                                                │  ← the contract  │
                                                └──────────────────┘
```

The **canonical JSON** is the heart. It is platform-agnostic. Everything before it is input plumbing. Everything after it is output plumbing. The schema for that JSON is per-product (WHEN Travel has one schema; another product has another), but the structure of how a schema is defined is universal — that is what this Bible specifies.

## 2. Anatomy of a Product Schema

Every product schema lives at `docs/schemas/<product>.md` and contains four sections.

### 2.1 Identity block — *who they are*
Universal. Always present.
- `name` (string, required)
- `phone` (string, nullable)
- `email` (string, nullable)
- `source_city` (string, nullable)
- `source` (string, nullable) — how they found us (referral / Instagram / WhatsApp / etc.)

### 2.2 Psychographic block — *what they want, why they want it*
Product-specific. The "soul" of the record.

For WHEN Travel: their dream destinations, the trigger moment, JTBD ("transformation they want").
For a financial coaching product: their money relationship, their fears, their definition of "rich".
For a fitness product: identity goals ("I want to be the kind of person who…"), trigger events.

### 2.3 Behavioral block — *what they are doing, where they are in the journey*
Product-specific. The "state" of the record.

For WHEN Travel: journey stage (Discovery Done / Plan Delivered / Active Saver / Milestone Unlocked / Trip Completed), milestones, savings activity.
For a fitness product: workout cadence, current programme, last check-in.

### 2.4 Blocker block — *what is stopping them*
Product-specific. The "friction" of the record.

For WHEN Travel: financial blocker, timing blocker, family blocker.
For most products: similar shape — money / time / belief / circumstance.

### 2.5 (Optional) Intelligence block — *what the AI infers*
Derived, not extracted directly. Confidence scores, recommended next action, sentiment, predicted timeline. Generated by a second LLM pass over the canonical JSON.

## 3. Schema File Format

Each `docs/schemas/<product>.md` is human-readable AND machine-readable. The machine-readable part is a fenced YAML block. The rest is documentation for humans.

```yaml
# Example fragment
product: when-travel
version: 1
fields:
  - slug: trip_budget
    title: "Budget Range"
    type: text           # text | number | checkbox | select | url | phone | email
    block: psychographic
    description: "Total trip budget mentioned by the client, as a string e.g. '1.5L' or '80000'"
    required: false
    sink_mapping:
      attio:
        object: people
        attribute: trip_budget
```

The extraction prompt is generated automatically from this YAML — humans never write prompts by hand. Add a field, the prompt updates.

## 4. The Extraction Prompt (template)

The LLM is given a generated system prompt of the form:

```
You are processing {{ input_type }} for {{ product_name }}.
{{ product_description }}

Return ONLY a valid JSON object — no markdown, no preamble.

{
  {{ for each field in schema: }}
  "{{ field.slug }}": {{ field.description }}, // {{ field.type }}
  {{ end }}
}

{{ if any select fields: render enum rules }}
{{ if multi-session input: render merge rules }}
```

Two rules baked into every prompt:
1. **Most-current wins.** If the input contains multiple sessions, the most recent state of a field overrides earlier mentions.
2. **Null is allowed.** Never invent. If a field isn't in the input, return `null`.

## 5. Adding a New Product

To onboard "WHEN Wellness" or "ZenStudio Coaching" or anything else:

1. Copy `docs/schemas/_template.md` to `docs/schemas/<product>.md`.
2. Fill in the YAML — identity block stays, swap out psychographic/behavioral/blocker blocks.
3. Run `python3 tools/attio-setup/create-fields.sh --schema <product>` (or skip, if the sink is not Attio).
4. Pass `--product <product>` to the extractor. The prompt regenerates from the schema. The sink writes to whatever Attio object/list (or other system) is mapped.

No code changes. New product = new YAML + new sink mapping.

---

## 6. Sink Adapters

A sink adapter takes the canonical JSON and writes it somewhere. Adapters are independent.

| Adapter | Writes to | Status |
|---------|-----------|--------|
| `attio` | Attio People + a per-product List | Live |
| `hubspot` | HubSpot Contacts + a list | Planned |
| `notion` | Notion database row | Planned |
| `sheets` | Google Sheets row | Planned |
| `stdout` | Pretty-printed JSON | Debug |

Each sink adapter reads `sink_mapping.<adapter>` from each field in the schema YAML. Unmapped fields are silently dropped at that sink.

## 8. Not in scope for v1

These belong here eventually but are not in v1:

- Multi-language input (Hindi / Hinglish handling — we currently rely on the LLM's native multilingual ability)
- Audio/video transcription (assume input is already text)
- Real-time streaming (current model is batch)
- Conflict resolution UI (when LLM extraction disagrees with human edits)
- Schema migrations (when a field changes type or gets renamed)

---

## 9. The Bible Rules

1. **No prompts in code.** Prompts are generated from the schema YAML.
2. **No field slugs in code.** Code reads them from the schema.
3. **No CRM API calls outside sink adapters.** Business logic never touches Attio directly.
4. **New product = new schema file.** Never fork the pipeline.
5. **Null over invention.** Better empty than wrong.

## 10. Known Failure Modes (learned in production)

### 10.1 Name matching must be fuzzy, not exact

CRM records can accumulate partial names from different sources. A record created by an old workflow may have `full_name = "Azharul"` while a new transcript yields `"Azharul Haque"`. Exact string match will miss this and create a duplicate.

**Rule:** Match on `full_name` first. If no exact match, fall back to `first_name` match. Keep the richer (longer) record.

**Cleanup:** Run `tools/attio-ingest/cleanup_duplicates.py --dry-run` to detect orphan partial-name records before each push. Run without `--dry-run` to delete them.

### 10.2 Always verify sink API field names against live API responses

The Attio list entries API returns `parent_record_id`, not `record_id`. Assuming field names without checking the actual response causes silent failures (empty set returned, check is skipped, every record re-tries the list-add on every run).

**Rule:** When reading fields from any API response, log the raw response once in dev and verify field names before shipping.

### 10.3 Commit order must match run order

If extraction and push happen in separate steps, the user must `git pull` between them. If the JSON is updated on the remote after the user already pulled, the push will run against a stale version — new records will silently not exist.

**Rule:** Always print the record count at the start of the push script and tell the user to verify it matches expectations before proceeding. If counts don't match, pull again.
